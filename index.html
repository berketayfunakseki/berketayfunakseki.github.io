Backend · Distributed systems · Cloud

Energy Connect Platform

TypeScript/Node.js connectivity layer for EV chargers and vehicles — my largest system.

ArchitectureSeparate API and worker processes over a durable PostgreSQL command queue
ReliabilityIdempotency keys, exponential-backoff retry, circuit breaker, dead-letter state
CloudAWS CDK → CloudFormation: ECS/Fargate, RDS, CloudWatch alarms, autoscaling

Problem. An energy platform sits in front of OEM APIs that time out, rate-limit and fail in ways the product above them must never notice. One flaky vendor cannot be allowed to degrade the whole platform — and a retried request must never start a car charging twice.

Solution. A connectivity layer built to isolate failure. Commands are written to a durable PostgreSQL queue with an idempotency key; workers claim rows using FOR UPDATE SKIP LOCKED so two workers never pick up the same command; every provider call is wrapped in retry plus circuit-breaker logic. Structured logs, Prometheus metrics and an SLO snapshot make failure visible, and a React operations dashboard shows device state, queue depth and SLO health. Backend tests run in GitHub Actions against a live PostgreSQL service container.

[React ops dashboard]      [client / integrator]
             \                    /
              v                  v
        [Node.js API — TypeScript]
                    | enqueue command + idempotency-key
                    v
        [PostgreSQL — devices + command_queue]
                    ^ FOR UPDATE SKIP LOCKED
                    |
           [Node.js worker pool]
                    | retry (exp. backoff) + circuit breaker
                    v
        [Simulated OEM A]   [Simulated OEM B]

 observability: structured JSON logs · Prometheus metrics · SLO snapshot
 infra: AWS CDK > CloudFormation > ECS/Fargate · RDS · CloudWatch alarms

// engineering decisions

  • Why a PostgreSQL queue instead of SQS or Kafka? Command state and queue state have to stay consistent with each other. Keeping both in one transactional database removes a whole class of "the message was sent but the row was never written" bugs — and at this scale a broker is infrastructure to justify, not use.
  • Why FOR UPDATE SKIP LOCKED? It lets several workers drain one table concurrently: each worker locks the rows it claims and skips whatever is already locked, so throughput scales with worker count instead of serialising behind one lock.
  • Why a circuit breaker on top of retries? Retrying against a provider that is already down turns one outage into a self-inflicted load test. The breaker trips after a failure threshold and fails fast until the provider recovers.
  • Why idempotency keys at the API edge? Clients retry. Without a uniqueness constraint on the key, a network hiccup silently becomes two START_CHARGING commands — invisible in tests, expensive in production.
  • Why AWS CDK rather than raw CloudFormation? The stack is typed TypeScript, so infrastructure is checked by the same compiler as the application. cdk synth still emits plain CloudFormation.

// lessons learned

  • Reliability code is only real if it is tested against failure. Retry and circuit-breaker units are tested with deliberately failing providers — proving the breaker actually opens is the whole point.
  • Splitting API and worker changed the design. Once the processes cannot share memory, every piece of coordination has to become explicit state in the database — which is what made the queue design necessary.
  • Next: real OEM adapters behind the existing provider interface, Grafana dashboards checked into the repo, blue/green deploys on ECS.

Project PARCA

Deterministic rules engine and game server for a multi-day, eight-player strategy game.

DeterminismSeeded RNG replays an entire season exactly — any result is reproducible
Testing146-case regression suite · currently 146 passed, 0 failed
ServerASP.NET Core · server-authoritative UTC clock · transfer ledger

Problem. A strategy game played over several days by eight people lives or dies on trust: if a result is disputed, it has to be provable — and no client can be allowed to touch a balance, a deadline or an outcome.

Solution. A deterministic rules engine in C#: a seeded RNG means an entire season can be replayed exactly, so any disputed result is reproducible and auditable. The ASP.NET Core server owns time (a server-authoritative UTC clock) and money (a transfer ledger), so no client can alter a balance, a deadline or a result. A 146-case regression suite covers eight negotiation minigames, transfer rules, elimination boundaries and season-end conditions.

// engineering decisions

  • Why a seeded RNG? Randomness that can be replayed turns "the game cheated me" into a question with an answer: re-run the season from the seed and compare.
  • Why server-authoritative time and money? Deadlines and balances are the two things a client would most want to change. Keeping both on the server — clock in UTC, every transfer in a ledger — removes that attack surface entirely.
  • Why a regression suite this early? Rules interact. Minigames, transfers and elimination boundaries all touch the same state, so every rule change re-runs all 146 cases.

// product side

  • I own the product as well as the code: design document, economy specification and a log of 14 recorded decisions, each tied to a testable hypothesis.
  • Pace: 174 commits in the first three weeks.

Data engineering · Orchestration

Analytics Data Platform

End-to-end batch pipeline: Airflow → PySpark → Parquet → PostgreSQL → dbt.

OrchestrationAirflow DAG drives ingest, transform, load and dbt build in order
TransformPySpark schema validation, typing and deduplication into Parquet
Modellingdbt staging + daily-sales mart, gated by data-quality tests

Problem. "I know SQL" and "I can build a data platform" are different claims. The second needs orchestration, a transformation engine, a warehouse, a modelling layer and tests that fail loudly when the data is wrong.

Solution. A reference pipeline that runs the whole loop: raw order events are validated, typed and deduplicated in PySpark, written as Parquet, loaded into a PostgreSQL warehouse, then modelled in dbt as a typed staging layer and a daily-sales fact table. The marts sit behind dbt data-quality tests, so a bad load fails the Airflow DAG instead of silently reaching a dashboard. Docker Compose reproduces everything locally with one command.

[data/raw/orders.csv]
        | ingest
        v
[PySpark — schema validation · typing · dedup]
        | write
        v
[Parquet — partition-friendly columnar]
        | load
        v
[PostgreSQL warehouse]
        |
        +-- dbt staging: stg_orders  (typed, cleaned)
        |
        +-- dbt mart:    fct_daily_sales  + schema.yml tests

 orchestration: Airflow DAG · env: Docker Compose · CI: GitHub Actions

// engineering decisions

  • Why Parquet between Spark and Postgres? Columnar output is cheap to re-read and re-load, so a failed load can be retried without re-running the Spark job.
  • Why dbt on top of SQL I could write by hand? Dependency-ordered builds, a documented schema, and tests that run as part of the pipeline rather than as a separate good intention.
  • Why deduplicate in Spark, not the warehouse? Deduplicating before the load keeps staging a faithful record of what arrived, not a place where cleaning silently happens.

// lessons learned

  • Orchestration is where the real design lives. Each step is easy alone; making them idempotent and re-runnable in a fixed order is what takes thought.
  • Next: incremental dbt models, partition-aware Spark writes and source freshness checks.

Jobscope

Swiss/EU job-market tracker — aggregates 200+ live listings from two APIs and ranks each 0–100 against my profile with TF-IDF cosine similarity.

FastAPIscikit-learnSQLiteJWTDocker
Case study

Problem. Tracking junior roles across Swiss and EU boards by hand meant duplicates, stale posts and no way to rank fit.

Solution. Fetch from RemoteOK and Adzuna, normalise URLs to kill duplicates, score every posting against a candidate profile with TF-IDF + cosine similarity, and serve it all through a JWT-authenticated FastAPI backend in Docker.

[RemoteOK API]   [Adzuna API]

// decisions

  • Why SQLite? Read-heavy with batch writes — a Postgres container adds ops cost for zero benefit at this scale.
  • Why TF-IDF over LLM embeddings? Job ads are keyword-dense; sparse vectors rank well at zero compute cost and no API dependency.
  • Lesson: the same posting appears on several boards under different URLs — normalising before hashing fixed silent double-counting.

SciPystatsmodelsFastAPIStreamlit
Case study

Solution. Power analysis to size a test, a two-proportion z-test with proper intervals, an SRM check that flags broken randomisation before anyone trusts a p-value, and a DiD estimator for when you can't randomise at all — the estimator family from my thesis.
